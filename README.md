# CodeLens

Single Go binary that generates a structured summary of any codebase.
Parses code with tree-sitter, summarizes each module via LLM, writes
a `CODELENS.md` file. On subsequent runs, diffs against the last
indexed commit and only re-summarizes what changed.

The output is a plain Markdown file. Any AI agent or human can read it
to understand the project without grepping through every file.

## Problem

AI coding agents spend 40-60% of their initial tool calls exploring a
codebase with grep/glob/read before doing useful work. There is no
standardized, pre-computed summary of "what does this project do and
how is it organized."

## Solution

```bash
codelens                     # first run: full index
codelens                     # next runs: incremental update (only changed modules)
codelens --full              # force full re-index
```

First run: parse everything, summarize every module, write `CODELENS.md`.
Next runs: `git diff --name-only <last-commit> HEAD`, re-summarize only
affected modules, update the file.

## Non-Goals

- Not a vector database or search engine
- Not an IDE plugin or language server
- Not a documentation generator (no API docs, no godoc, no javadoc)
- Not a code review tool
- Does not run a server, watch files, or stay resident

### Flow: First Run

```
main
 ├─ config.Load()                    # flags + config file + env vars
 ├─ parser.Parse(repoRoot)           # tree-sitter -> []Module{files, symbols}
 ├─ graph.Build(modules)             # imports -> dependency graph
 ├─ summarizer.SummarizeAll(modules) # LLM call per module (parallel, bounded)
 ├─ output.Write(summary, graph)     # assemble CODELENS.md
 └─ state.Save(commitHash, modules)  # persist to .codelens/state.json
```

### Flow: Incremental Update

```
main
 ├─ config.Load()
 ├─ state.Load()                           # read last indexed commit
 ├─ diff.Changed(lastCommit, HEAD)         # git diff --name-only
 ├─ diff.AffectedModules(changedFiles)     # map files -> modules
 ├─ parser.Parse(repoRoot)                 # re-parse all (fast, no LLM)
 ├─ graph.Build(modules)                   # rebuild graph (fast, no LLM)
 ├─ summarizer.SummarizePartial(affected)  # LLM only for changed modules
 ├─ output.Write(summary, graph)           # re-assemble full CODELENS.md
 └─ state.Save(HEAD, modules)              # update state
```

### Incremental Diff Algorithm

```
function update():
    state = read(".codelens/state.json")
    if state is null:
        return full_index()

    changed_files = git_diff_names(state.lastCommit, "HEAD")
    if empty(changed_files):
        print("Nothing changed since last index")
        return

    affected_modules = set()
    for file in changed_files:
        module = resolve_module(file)
        if module != null:
            affected_modules.add(module)

    all_modules = parse_all()
    graph = build_graph(all_modules)

    for module in affected_modules:
        module.summary = llm_summarize(module)

    for module in all_modules - affected_modules:
        module.summary = cached_summary(module)

    project_summary = llm_summarize_project(all_modules)
    write_markdown(project_summary, all_modules, graph)
    save_state(git_head(), all_modules)
```

Edge cases:
- **New module**: in parser output but not in state -> summarize it
- **Deleted module**: in state but not in parser output -> remove from output
- **Files moved between modules**: both old and new module re-summarized
- **No git repo**: always full index, warn user
- **Dirty working tree**: index working tree, store HEAD + dirty flag

## Module Resolution per Language

Different languages organize code differently. The parser must resolve
"which module does this file belong to?" per language:

| Language | Module unit | Resolution |
|----------|-------------|------------|
| **Go** | Package (directory) | Directory path. internal/agent/*.go -> module internal/agent |
| **Java** | Package | package com.example.auth; declaration in file. Group files by declared package. Nested packages are separate modules |
| **TypeScript** | Directory or barrel export | Directory containing index.ts, or directory path. src/components/*.tsx -> module src/components |
| **Python** | Package (directory with __init__.py) or single-file module | Directory with __init__.py -> module. Standalone .py -> module |
| **Rust** | Crate or mod | Cargo.toml defines crate boundary. <mod.rs> or <lib.rs> defines submodules |

### Java-Specific Considerations

Java projects have unique structural patterns that the parser must handle:

- **Package declaration**: the package statement in each .java file
  determines the module, not the directory path (though they conventionally
  match). Use the parsed package statement as source of truth.
- **Build tool layouts**: recognize Maven (src/main/java/, src/test/java/)
  and Gradle (app/src/main/java/) conventional directories. Strip the
  build prefix when computing module names — src/main/java/com/example/auth/
  -> module com.example.auth, not src/main/java/com/example/auth.
- **Test sources**: files under src/test/java/ are associated with their
  matching src/main/java/ module. Don't create separate test modules.
- **Multi-module projects**: Maven/Gradle multi-module builds have multiple
  pom.xml/build.gradle files. Each subproject is a top-level grouping.
  Module names become subproject:com.example.auth.
- **Annotations**: extract key annotations (@RestController, @Service,
  @Repository, @Entity, @Configuration) as metadata — they indicate
  the role of a class in the architecture (Spring conventions).
- **Interfaces vs implementations**: Java relies heavily on interface/impl
  patterns. Extract both and note the relationship in the summary.
- **Visibility**: public classes/methods are the module's API.
  package-private and private are internal. Summarize the public API.

## LLM Prompts

### Module Summary

```
System: You are a code analyst. Given a module's source symbols,
write a concise summary. Be specific — use actual type and function
names. 3-5 sentences max.

User:
Module: {path}
Language: {language}
Files: {file_list}
Symbols:
---
{symbol_signatures}
---

Respond with exactly this format:
**Responsibility**: <2-3 sentences>
**Key types**: <comma-separated>
**Key functions**: <comma-separated>
```

### Project Summary

After all modules are summarized, one LLM call with all module
summaries + dependency graph as input -> 2-3 paragraph overview.

### Token Management

- Large files: send only exported symbols (signatures, not bodies)
- Very large modules (>50 files): top 50 by LOC, note "and N more"
- Parallel LLM calls with bounded concurrency (default: 5)

## Language Support

tree-sitter grammars, priority order:

| Priority | Language | Grammar | Module Unit |
|----------|----------|---------|-------------|
| P0 | Go | tree-sitter-go | directory (package) |
| P0 | Java | tree-sitter-java | package declaration |
| P0 | TypeScript / JavaScript | tree-sitter-typescript | directory |
| P0 | Python | tree-sitter-python | directory with __init__.py |
| P1 | Rust | tree-sitter-rust | crate / mod |
| P2 | C / C++ | tree-sitter-c, tree-sitter-cpp | directory |
| P2 | Ruby | tree-sitter-ruby | directory |

Unsupported languages: file listing + LOC count only (no AST),
still included in CODELENS.md with basic info.

## Success Criteria

1. Full index on a 200-file Go project completes in under 60 seconds
2. Full index on a 500-file Java project completes in under 120 seconds
3. Incremental update on a 5-file change completes in under 10 seconds
4. An AI agent reading CODELENS.md can answer "what does module X do?"
   without additional grep/read calls
5. Single static binary, no runtime dependencies beyond an LLM API key
6. Works on Go, Java, TypeScript, and Python projects out of the box
7. Correctly resolves Java package structure in Maven and Gradle projects
